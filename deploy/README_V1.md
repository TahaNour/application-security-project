A1 – Squelette Maven multi-modules### ObjectifDonner au projet une structure commune pour que trois personnes travaillent chacune dans leur module sans se marcher dessus.### Structure```application-security-project/├─ pom.xml                 (POM parent, packaging pom)├─ traceit-crypto/         (jar)  propriétaire B├─ traceit-hiding/         (jar)  propriétaire C├─ traceit-bench/          (jar)  propriétaire C├─ traceit-api/            (war)  propriétaire B├─ frontend/               (React + Vite, plus tard)├─ deploy/                 (scripts .cli, .properties, deploy.sh)├─ .github/workflows/ci.yml├─ .gitignore└─ .gitattributes```### Contenu du POM parent- `<modules>` : liste des quatre modules.- `maven.compiler.release = 25`.- `dependencyManagement` : API Jakarta EE 11 (`jakarta.jakartaee-api:11.0.0`, scope `provided`), JUnit 5 (BOM) et ArchUnit (scope `test`). Les modules enfants déclarent ces dépendances **sans version**.- `pluginManagement` : versions des plugins compiler, surefire, jar et war.### Dépendances entre modules- `traceit-bench` dépend de `traceit-hiding`.- `traceit-api` dépend de `traceit-crypto` et `traceit-hiding`, de l'API Jakarta (`provided`) et d'ArchUnit (`test`).- Le WAR est nommé `api-${project.version}` → `traceit-api/target/api-1.0.war`. Ce format `nom-version.war` est celui qu'attend le script `add-api.cli` du professeur.### Interfaces figées (contrat entre A, B et C)| Interface | Module | Propriétaire ||---|---|---|| `CryptoService` (`encrypt`, `decrypt`, objectId en AAD) | `traceit-crypto` | B || `SigningService` (`sign`, `verify`, Ed25519) | `traceit-crypto` | C || `WatermarkEngine` (`embed`, `extract`, `Optional.empty()` = « Indéterminé ») | `traceit-hiding` | C |Elles ne changent pas sans prévenir toute l'équipe. B code contre elles avec une implémentation factice pendant que C écrit la vraie.### Fichiers de protection- `.gitignore` : exclut `target/`, `*.p12`, `*.jks`, `*.pem`, `*.key`, `.env`, `node_modules/`, `dist/`. Un certificat ou un secret ne part donc pas dans Git par accident.- `.gitattributes` : force `eol=lf` pour `*.sh`, `*.cli`, `*.properties`. Sans cela, un script enregistré sous Windows (fins de ligne CRLF) plante sous Linux et dans la CI.### Vérification```bashmvn -B verifyls traceit-api/target/*.war      # api-1.0.war```Résultat attendu : `BUILD SUCCESS` pour les 5 projets (parent + 4 modules).> Les numéros de version des plugins et d'ArchUnit n'ont pas pu être vérifiés à la rédaction. Si une version est introuvable ou si ArchUnit refuse le bytecode Java 25, la corriger dans le POM parent (propriétaire : A) et prévenir B.---## 3. A2 – Pipeline CI (GitHub Actions)### ObjectifÀ chaque `push` et chaque `pull request`, une machine neutre vérifie que le projet compile, que les tests passent et qu'aucun secret n'a été commité.### Fichier `.github/workflows/ci.yml````yamlname: CIon: [push, pull_request]permissions: { contents: read }jobs:  build:    runs-on: ubuntu-latest    steps:      - uses: actions/checkout@v4      - uses: actions/setup-java@v4        with: { distribution: temurin, java-version: '25', cache: maven }      - run: mvn -B verify  gitleaks:    runs-on: ubuntu-latest    steps:      - uses: actions/checkout@v4        with: { fetch-depth: 0 }      - uses: gitleaks/gitleaks-action@v2        env: { GITHUB_TOKEN: "${{ secrets.GITHUB_TOKEN }}" }```### Les deux jobs| Job | Rôle ||---|---|| `build` | Récupère le code, installe Temurin 25 avec cache Maven, lance `mvn -B verify` (compilation de tous les modules + tests, dont le futur test d'architecture de B) || `gitleaks` | Récupère tout l'historique (`fetch-depth: 0`) et scanne chaque commit à la recherche de secrets |### Hook local gitleaks (chaque membre doit l'installer)```bashprintf '#!/bin/sh\ngitleaks git --pre-commit --staged --redact -v\n' > .git/hooks/pre-commitchmod +x .git/hooks/pre-commit```Le hook n'est pas versionné (`.git/hooks/` reste local). La CI est donc le filet de sécurité.### Protection de `main`GitHub → Settings → Branches (ou Rulesets) → règle sur `main` :- Require a pull request before merging- Require status checks to pass : `build` et `gitleaks`Les checks n'apparaissent dans la liste qu'après leur première exécution.### Test de réussite (faux secret)Sur une branche jetable, jamais fusionnée :```bashgit checkout -b test/fake-secretecho 'API_KEY="<your-api-key>"' > secret-test.txtgitleaks dir secret-test.txtgit add secret-test.txtgit commit --no-verify -m "test: faux secret"git push -u origin test/fake-secret     # le job gitleaks doit être rouge```Nettoyage : supprimer la branche locale et distante.---## 4. A3 – WildFly en HTTPS (TLS 1.3)### ObjectifServir WildFly en HTTPS avec TLS 1.3 uniquement, sur des noms `*.traceit.local`, avec un certificat de développement que le navigateur Windows accepte sans avertissement.### Étape 1 – Compte administrateur nominatif```bash$JBOSS_HOME/bin/add-user.sh```Type `a` (Management User), identifiant **nominatif** (pas `admin`), mot de passe fort. La console http://127.0.0.1:9990 n'écoute que sur 127.0.0.1.### Étape 2 – mkcert côté Windows (PowerShell)```powershellwinget install FiloSottile.mkcertmkcert -installmkcert -CAROOT````mkcert -install` crée une autorité locale et l'ajoute au magasin de confiance de Windows. Redémarrer le navigateur ensuite.### Étape 3 – mkcert côté Ubuntu avec la même autorité```bashsudo apt install -y mkcertecho 'export CAROOT="/mnt/c/Users/<NOM_WINDOWS>/AppData/Local/mkcert"' >> ~/.bashrcsource ~/.bashrcls "$CAROOT"        # rootCA.pem et rootCA-key.pem````<NOM_WINDOWS>` peut différer du nom Ubuntu (`ls /mnt/c/Users` pour le retrouver). Ne pas lancer `mkcert -install` dans Ubuntu.### Étape 4 – Générer le certificat```bashcd /tmpmkcert -pkcs12 -p12-file traceit.p12 traceit.local "*.traceit.local"cp traceit.p12 $JBOSS_HOME/standalone/configuration/chmod 600 $JBOSS_HOME/standalone/configuration/traceit.p12rm traceit.p12```Le mot de passe par défaut de mkcert est `changeit` (dev seulement). Le fichier `.p12` et `rootCA-key.pem` ne sont **jamais** commités.### Étape 5 – Fichier hosts de WindowsBloc-notes **en administrateur**, fichier `C:\Windows\System32\drivers\etc\hosts`, ajouter :```127.0.0.1 traceit.local www.traceit.local api.traceit.local admin.traceit.local```C'est le fichier de **Windows** qui compte, car c'est le navigateur Windows qui résout les noms. Vérification : `ping www.traceit.local` doit indiquer `127.0.0.1`.### Étape 6 – Configuration TLS 1.3 dans WildFlyScript `deploy/tls-dev.cli` (WildFly doit déjà tourner) :```/subsystem=elytron/key-store=httpsKS:add(path=traceit.p12,relative-to=jboss.server.config.dir,credential-reference={clear-text=changeit},type=PKCS12)/subsystem=elytron/key-manager=httpsKM:add(key-store=httpsKS,credential-reference={clear-text=changeit})/subsystem=elytron/server-ssl-context=httpsSSC:add(key-manager=httpsKM,protocols=[TLSv1.3])/subsystem=undertow/server=default-server/https-listener=https:write-attribute(name=ssl-context,value=httpsSSC)reload``````bash$JBOSS_HOME/bin/jboss-cli.sh --connect --file=deploy/tls-dev.cli```Le PDF de la roadmap contient deux fautes de frappe dans ces commandes (`relativeto` au lieu de `relative-to`, `cleartext` au lieu de `clear-text`) ; la version ci-dessus est corrigée.### Étape 7 – Vérifications```bash# Contexte appliqué ?$JBOSS_HOME/bin/jboss-cli.sh --connect --command="/subsystem=undertow/server=default-server/https-listener=https:read-attribute(name=ssl-context)"# attendu : httpsSSC# Protocoles autorisés ?$JBOSS_HOME/bin/jboss-cli.sh --connect --command="/subsystem=elytron/server-ssl-context=httpsSSC:read-attribute(name=protocols)"# attendu : ["TLSv1.3"]# Poignée de main TLS 1.3 depuis Ubuntucurl -v --cacert "$CAROOT/rootCA.pem" --resolve www.traceit.local:8443:127.0.0.1 https://www.traceit.local:8443 -o /dev/null# TLS 1.2 doit être refusé (code 000 = refus, résultat attendu)curl -sk --tls-max 1.2 --resolve www.traceit.local:8443:127.0.0.1 https://www.traceit.local:8443 -o /dev/null -w "%{http_code}\n"```Dans le navigateur Windows : `https://www.traceit.local:8443` doit afficher un cadenas sans avertissement.### Ce qui n'est pas encore faitLes en-têtes **HSTS** et **nosniff** et les ports 80/443 arrivent avec A4 (scripts `.cli` du professeur). Le critère « `curl -I https://www.traceit.local` renvoie HSTS et nosniff » n'est donc atteint qu'après A4.---## 5. Notions à savoir expliquer### 6.1 Workflow, job, step- **Workflow** : un fichier YAML dans `.github/workflows/` qui décrit une automatisation déclenchée par un événement (`on: [push, pull_request]`).- **Job** : un groupe d'étapes exécuté sur une machine propre et indépendante (`ubuntu-latest`). Deux jobs tournent en parallèle et ne partagent ni fichiers ni outils.- **Step** : une action (`uses:`) ou une commande (`run:`) à l'intérieur d'un job, exécutée dans l'ordre.Le `checkout` n'est pas un job : c'est la première étape de chacun des deux jobs, car chaque job démarre sur une machine vide.### 6.2 Pourquoi deux jobs séparés (`build` et `gitleaks`)Parallélisme (CI plus rapide), diagnostic clair (on sait si c'est le code ou un secret), réglages différents (`gitleaks` a besoin de tout l'historique, `build` de Java et du cache Maven), et possibilité d'exiger chaque check séparément sur `main`.### 6.3 Pourquoi un POM parentSans parent, chaque module aurait sa propre version de Java, de JUnit et de plugins, et elles divergeraient avec trois personnes. Le parent centralise ces valeurs (une modification, tous les modules suivent), permet de tout construire avec un seul `mvn -B verify` dans le bon ordre, et `dependencyManagement` fixe les versions sans conflit.### 6.4 `provided` contre un scope normal| Scope | Compilation | Exécution | Embarqué dans le WAR ||---|---|---|---|| `compile` (défaut) | oui | oui | oui || `provided` | oui | non, fourni par le serveur | non || `test` | tests seulement | non | non |Jakarta EE est en `provided` parce que WildFly contient déjà l'implémentation. L'embarquer aussi créerait deux copies des mêmes classes (conflits de chargement, WAR plus lourd, comportements imprévisibles). Une bibliothèque que WildFly n'a pas (par exemple Bouncy Castle pour Argon2id) sera en `compile`.### 6.5 Ce que fait gitleaksUn scanner de secrets : il parcourt les fichiers et l'**historique Git** (expressions régulières + entropie) à la recherche de mots de passe, clés API, jetons et clés privées. Un secret supprimé dans un commit récent reste lisible dans l'historique et sur GitHub, d'où `fetch-depth: 0` pour scanner tous les commits.### 6.6 Pourquoi gitleaks à deux endroits (hook local et CI)C'est de la **défense en profondeur**.- **Hook local** : agit avant le commit, le secret n'entre jamais dans l'historique. Limite : non versionné, donc oubliable ou contournable avec `--no-verify`.- **CI** : agit après le push, côté serveur, sur une machine que personne ne peut désactiver depuis son poste. Elle rattrape un hook absent ou contourné. Mais le secret serait alors déjà sur GitHub (à révoquer et régénérer).### 6.7 Pourquoi la protection de `main` rend la CI contraignanteSans protection, la CI est informative : rouge ou vert, mais n'empêche rien. Avec « Require status checks » et « Require a pull request », le bouton de fusion est bloqué tant que `build` et `gitleaks` ne sont pas verts, et on ne peut plus pousser directement sur `main`. Le code qui ne compile pas, échoue aux tests (dont le test d'architecture) ou contient un secret n'entre pas dans `main`.### 6.8 Les quatre objets Elytron| Objet | Rôle ||---|---|| **key-store** (`httpsKS`) | Le coffre : charge le fichier `traceit.p12` (certificat + clé privée) || **key-manager** (`httpsKM`) | Va chercher dans le coffre la clé et le certificat à présenter pendant la poignée de main TLS || **server-ssl-context** (`httpsSSC`) | Regroupe les règles de la connexion : key-manager + protocole autorisé (TLS 1.3 uniquement) || **https-listener** (Undertow) | Le port 8443 lui-même ; la commande `write-attribute ssl-context` lui dit d'utiliser `httpsSSC` |En résumé : le fichier contient les secrets, le key-manager les sert, le contexte fixe les règles, l'écouteur les applique sur le port.### 6.9 Pourquoi `changeit` n'est acceptable qu'en devC'est le mot de passe par défaut, connu de tous. Il protège le `.p12` qui contient la clé privée : quiconque lit le fichier peut l'ouvrir. En dev, le certificat n'est valable que sur la machine locale, donc le risque est nul. En production, il faut un mot de passe fort stocké dans le **credential store Elytron**, pas en clair (SEC-CRYP-02).### 6.10 Pourquoi la console 9990 reste sur 127.0.0.1La console permet de déployer n'importe quelle application et de tout reconfigurer : avec un mot de passe faible, un attaquant peut déployer un WAR malveillant et prendre le contrôle du serveur (menace TS-40). Écouter uniquement sur `127.0.0.1` la rend inaccessible depuis l'extérieur ; en production on y accède par tunnel SSH. C'est du moindre privilège et de la réduction de surface d'attaque (SEC-DEPL-04).### 6.11 Pourquoi mkcert plutôt qu'un certificat auto-signéUn certificat auto-signé est inconnu des navigateurs : avertissement à chaque visite, et l'utilisateur prend l'habitude de l'ignorer. mkcert crée une **autorité de certification locale**, l'installe dans le magasin de confiance de Windows, puis signe les certificats avec elle. Le navigateur vérifie la chaîne et affiche un cadenas sans avertissement, avec un comportement identique à la production (utile pour tester HSTS, les cookies `Secure` et le service worker, qui exigent un vrai HTTPS de confiance). Avec une CA partagée entre Windows et WSL (variable `CAROOT`), les certificats générés dans Ubuntu sont aussi reconnus par le navigateur Windows. `rootCA-key.pem` reste secrète.### 6.12 Pourquoi TLS 1.3Il supprime les algorithmes obsolètes (MD5, SHA-1, RC4, 3DES, AES-CBC), impose la confidentialité persistante (forward secrecy) pour toutes les suites, retire les fonctionnalités vulnérables (export ciphers, RSA key transport) et accélère la poignée de main. Un client limité à TLS 1.2 est refusé : c'est voulu (SEC-CONF-01).### 6.13 Pourquoi un seul WildFly à la fois, et `reload`WildFly occupe les ports 8080, 8443 et 9990. Un second `standalone.sh` plante avec `Address already in use`. La commande `jboss-cli.sh --connect` se connecte au serveur déjà lancé (port 9990) et lui envoie des ordres ; `reload` recharge la configuration sans redémarrer le processus. Avant de fermer VS Code, arrêter WildFly proprement (`Ctrl+C` ou `jboss-cli.sh --connect --command=shutdown`), car fermer le terminal ne tue pas toujours le processus Java.### 6.14 Pourquoi le fichier hosts de WindowsLes noms `*.traceit.local` n'existent pas sur Internet. Le fichier hosts est un carnet d'adresses local consulté avant le DNS : `127.0.0.1 www.traceit.local` redirige le nom vers la machine locale. Le navigateur tourne sous Windows, donc c'est le fichier de Windows qui compte (pas `/etc/hosts` d'Ubuntu).---## 7. Problèmes rencontrés et solutions| Symptôme | Cause | Solution ||---|---|---|| `libjli.so: cannot open shared object file` | JDK SDKMAN incomplet ou shell non rechargé | `source ~/.sdkman/bin/sdkman-init.sh` ; réinstaller si besoin || `404` sur le `wget` de WildFly | `XX` laissé comme espace réservé | Utiliser la vraie version (`42.0.0.Final`) || `Repository not found` au clone | Faute dans l'URL du PDF | Utiliser `application-security-project` (avec tiret) || `Author identity unknown` | Identité Git non définie | `git config --global user.name` et `user.email` || `Address already in use` (8080, 8443, 9990) | Un WildFly déjà lancé | Arrêter l'ancienne instance puis relancer || `ERR_CONNECTION_CLOSED` / `SSL_ERROR_SYSCALL` | Contexte TLS non appliqué ou serveur en `reload-required` | Vérifier `ssl-context`, `server-state`, lancer `reload` || `curl --tls-max 1.2` renvoie `000` | Comportement attendu (TLS 1.2 refusé) | Rien à corriger |---## 8.
